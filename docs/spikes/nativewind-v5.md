### BLOCKER: Tailwind v4 CSS import incompatible with react-native-css 3.0.7

`react-native-css@3.0.7` (NativeWind v5's CSS engine) uses a **double-LightningCSS-pass** architecture:
1. First pass: Expo's Metro worker transforms the `.css` file with `platform: "web"` + PostCSS
2. Second pass: react-native-css's `compile()` function processes the resulting CSS string using its own LightningCSS calls

**Failure:** Tailwind v4.3.0's CSS output contains constructs that cause LightningCSS 1.32.0 (the latest released version — no upgrade possible) to fail the second pass deserialization:

- `@source "../../packages/ui/src"` — Tailwind v4 content-scanning directive; LightningCSS does not recognise it: `Warning: Unknown at rule: @source` → `Error: failed to deserialize; expected a sequence, found ()`
- `@import "tailwindcss"` / `@import "tailwindcss/theme"` — includes Tailwind v4's preflight and theme CSS; preflight contains `@supports (not (-webkit-appearance: -apple-pay-button)) /* Not Safari */ or (contain-intrinsic-size: 1px) /* Safari 17+ */` — inline comments inside `@supports` conditions cause the double-pass serialisation roundtrip to fail: `Error: failed to deserialize; expected an object-like struct named Specifier, found ()`
- `@theme default {}` — non-standard NativeWind at-rule in `nativewind/theme.css`; also causes deserialization failure

**Workaround applied:** Removed all `@import "tailwindcss"` directives from `global.css`. Used hand-crafted plain CSS utility classes instead (`.p-4`, `.rounded-lg`, etc.). This workaround allows Metro to bundle without errors but **defeats the purpose of NativeWind** — developers must manually maintain a CSS utility library rather than using Tailwind's generated utilities.

**Impact on AC-1:** CSS custom property resolution with `bg-[--spike-bg]` was NOT fully testable using the intended Tailwind workflow. The spike component uses CSS custom properties in `global.css` (`--spike-bg`, `--spike-text`) defined as plain CSS variables (not Tailwind tokens), which is a degraded validation.

## 3. Hot Reload Timing

Device: iPhone 17 Pro Simulator (iOS 26.3, JSC)

### BLOCKER: NativeWind metro transform causes runtime failure in Expo Go

NativeWind v5.0.0-preview.3's custom Metro transformer (`react-native-css/metro/metro-transformer.js`) replaces Expo's default Metro transformer. This causes a JS runtime error that prevents the app from loading in Expo Go 54.0.6:

```
[runtime not ready]: TypeError: getDevServer is not a function (it is Object)

createWebSocketConnection
&platform=ios&dev=true&hot_file=hermes-stable:107111:32

anonymous
&platform=ios&dev=true&hot_file=hermes-stable:107120:27

loadModuleImplementation
&platform=ios&dev=true&hot_rofile=hermes-stable:252:40

guardedLoadModule
&platform=ios&dev=true&hot_rofile=hermes-stable:165:37

metroRequire
&platform=ios&dev=true&hot_Profile=hermes-stable:78:91
```

**Isolation confirmed:** Running the same project WITHOUT the NativeWind metro transform (reverted `metro.config.js` to standard `getDefaultConfig` with no `withNativewind` wrapper) produces no `getDevServer` error. The error is directly caused by `withNativewind(config, ...)` in metro.config.js.

**Root cause analysis:** The custom metro-transformer replaces Expo's `unstable_transformerPath` with its own wrapper. For non-CSS files, it delegates to the original transformer. However, some aspect of the module resolution chain or the injected `StyleCollection` initialisation code (from the compiled `global.css` module) appears to corrupt the Metro HMR client's ability to access `DevSettings.getDevServer` as a callable function on Expo SDK 54.0 / RN 0.81.6 + Expo Go 54.0.6.

**`globalClassNamePolyfill: false` tested:** Disabling the module interception polyfill (`withNativewind(config, { globalClassNamePolyfill: false })`) did not resolve the error. The issue is not in the module aliasing layer.

**Story notes confirmation:** The story Dev Notes state "Expo Dev Client required — NativeWind v5-preview requires Dev Client." This is confirmed. Expo Go is not a valid test environment for NativeWind v5-preview.

## 5. Additional Findings

### react-native-reanimated undocumented dependency

`react-native-css@3.0.7` includes `react-native-css/dist/module/native/reanimated.js` which is conditionally required for animated `className` features. Even when no animated className is used, Metro resolves this path and errors if `react-native-reanimated` is not installed:

```
Unable to resolve "react-native-reanimated" from "react-native-css/dist/module/native/reanimated.js"
```

**Workaround applied:** Created `apps/mobile/src/stubs/react-native-reanimated.js` with a minimal passthrough stub and mapped it via `config.resolver.extraNodeModules`. This is an undocumented dependency not listed in NativeWind v5-preview documentation.

### Dev Client build required

NativeWind v5.0.0-preview.3 is **not compatible with Expo Go**. A Dev Client build is required for both development iteration and spike validation. This is a significant development overhead:
- EAS Dev Client build required (or local native build with `expo run:ios` / `expo run:android`)
- Full native rebuild whenever NativeWind or its native deps change
- CI/CD must produce Dev Client builds for all team members

## 6. Decision

### Result: FALLBACK

**Triggering failures:**

1. **AC-1 FAIL — LightningCSS double-pass incompatibility**: `@import "tailwindcss"` in `global.css` causes `react-native-css@3.0.7`'s metro transformer to fail. Tailwind v4.3.0's CSS output is incompatible with LightningCSS 1.32.0's serialization roundtrip. This is the current latest LightningCSS version — no upgrade path exists. Without `@import "tailwindcss"`, Tailwind utility classes are not available; developers must hand-write CSS utilities. This defeats the primary value proposition of NativeWind.

2. **AC-1 / AC-2 / AC-3 BLOCKED — Runtime failure in Expo Go**: NativeWind's custom metro transformer causes `getDevServer is not a function` runtime error. App cannot load. No visual validation, no a11y prop inspection, and no hot reload timing measurement were possible in the available Expo Go environment. A Dev Client build was not available within the spike time-box.

**Fallback adopted:** StyleSheet-based components with explicit a11y props replace NativeWind v5 in `packages/ui`.

**Effort estimate for fallback path across Epics 2–4:** ~2–3 days re-baselining affected stories (labelling + estimates); individual component stories are not significantly affected — StyleSheet patterns are straightforward and well-understood. Total implementation effort increase is minimal (StyleSheet.create vs Tailwind className — roughly equivalent).

**ADR revision:** `docs/spikes/nativewind-v5-fallback-adr.md`

**What additional testing would confirm the result (if retried):**
- Build a Dev Client (EAS or `expo run:ios`) with NativeWind v5-preview.4 (one version newer than tested)
- Verify `@import "tailwindcss"` compiles without LightningCSS error on preview.4
- Run spike component on physical Android (2GB RAM, Hermes) and verify CSS vars resolve to indigo
- If both pass: AC-1 confirmed; re-run AC-2 (a11y) and AC-3 (hot reload) on both platforms
- Even if a fix is found, the Dev Client overhead remains; teams should weigh that cost

**Stories unblocked by this FALLBACK decision:**
- 1-4-token-system-and-typography-architecture: proceed with StyleSheet tokens, not Tailwind tokens
- 1-5-motion-layout-and-mode-foundations: use Reanimated directly, not NativeWind animation utilities
- 1-6-developer-infrastructure-i18n-scaffold-and-accessibility-gates: use raw RN a11y props
- All Epic 2–7 packages/ui component stories: must be re-baselined before sprint entry (see fallback ADR)
