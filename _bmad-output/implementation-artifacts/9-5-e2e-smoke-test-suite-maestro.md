## Story

As a developer releasing to production,
I want a CI-gated Maestro smoke suite covering the critical therapy loop,
so that a regression in the core user path is caught before it reaches users.

## Acceptance Criteria

1. **Given** Maestro is not yet configured in the project (confirmed: no `.maestro/` directory, no `maestro` reference anywhere in the repo) **When** this story is implemented **Then** `apps/mobile/.maestro/` is created containing 5 flow files (see AC2) plus a `setup/` subdirectory for shared `runFlow:`-able subflows and `runScript:`-able JS helpers (see Dev Notes § Shared setup pattern); a new root script `"ci:e2e"` is added to `package.json` invoking a new `scripts/ci/run-e2e-smoke.sh` (model its structure on `scripts/ci/verify-schema-drift.sh` — `set -euo pipefail`, env-var-overridable paths/ports); a new job is added to `.github/workflows/ci.yml` (model its shape on the existing `build`/`typecheck`/`lint`/`test` jobs — `actions/checkout@v4`, `pnpm/action-setup@v4`, `actions/setup-node@v4`) that runs `pnpm ci:e2e` on `ubuntu-latest`, gating merges to `main` the same way the other CI jobs already do. **Architecture decision — read before starting (Task 1 is a feasibility spike, do this first):** this story requires three infrastructure pieces that don't exist yet in this repo and must be stood up together: (a) a hardware-accelerated Android emulator in CI, (b) a locally-built (not EAS-cloud) Expo custom dev client APK, (c) a local Supabase backend reachable from that emulator. See Dev Notes § CI Architecture Decisions for the full rationale and the exact mechanics of each — do not improvise a different approach (e.g. Maestro Cloud, EAS cloud builds, or testing against the real `.env` Supabase project) without re-confirming the tradeoffs documented there, since those alternatives were considered and rejected for stated reasons (cost, and contaminating production data). This "do not improvise" constraint applies to the four architecture decisions themselves (platform/runner choice, build mechanism, backend, test-account state strategy) — it does not override the implementation-detail fallbacks Task 1.2, Task 1.4, and Task 8.3 already pre-authorize. If Task 1's spike finds the Android/KVM/`ubuntu-latest` path infeasible, this AC's "hardware-accelerated Android emulator" condition is satisfied by Task 1.4's documented fallback platform instead, not violated by it.

2. **Given** the critical path flows **When** the smoke suite runs **Then** the following YAML flow files exist and pass, run independently against a fresh `supabase db reset` backend state (per Maestro's own best practice that "each Flow should be able to run on a completely reset device/state" — do **not** rely on one flow's UI actions leaving state for the next; see Dev Notes § Flow independence):
   1. `onboarding.yaml` — app launch through **real** account creation (OTP request → fetch the code from local Mailpit via a `runScript` HTTP call, see Dev Notes § OTP retrieval — do **not** use the `__DEV__`-only "DEV: Sign in as test user" bypass button here, since this flow exists specifically to catch regressions in the real signup/OTP path), through the assessment screen (psychoeducation + SUDS-calibration widget — there is no separate SPIN/symptom-check screen in the current implementation, contrary to the epics' phrasing; `assessment.tsx` is the single combined screen), to adding one fear-ladder item with a SUDS rating and reaching `complete.tsx`'s "Start your journey" button.
   2. `ladder-build.yaml` — independently signs in (via the DEV bypass into `test1@test.com`, see Dev Notes § On-device vs. server-side state for why this account's onboarding-complete status is **not** backend-seedable and must instead come from a shared idempotent "ensure onboarded" subflow), adds at least one fear item with a SUDS rating via the **standalone** ladder editor (`apps/mobile/app/ladder.tsx`, distinct from the onboarding ladder builder already covered by flow 1 — exercising both gives broader coverage), and asserts the home screen reaches the `'morning'` state (the `CourageLadderEntryCard` from `@exposure-buddy/ui` is visible — this is the literal screen state epics.md calls "Start today's challenge", there is no screen or button with that exact label).
   3. `exposure-loop.yaml` — independently signs in (same DEV-bypass + ensure-onboarded pattern as flow 2) against a backend-seeded pending ladder item (`fear_ladder_items` is a real Postgres table written via PostgREST during setup — see Dev Notes § CI Architecture Decisions and Task 1.5 for the still-open question of whether a PowerSync sync stream must also be reachable in CI for that seeded row to appear in the on-device UI this flow drives), starts a session, selects a technique, advances through intent (pre-SUDS) and the forward-only briefing screen, begins exposure, logs one SUDS reading, completes the exposure, and reaches the debrief screen.
   4. `debrief.yaml` — continues from a freshly-completed exposure (this flow's own `onFlowStart` setup must drive the session to the debrief screen itself, same as flow 3, via a shared `runFlow:` subflow — see Dev Notes — rather than assuming flow 3 already left the app in that state), fills the optional reflection field, taps "Done", and verifies the home screen no longer shows the `'progressing'` state for that item (it shows `'morning'` if other pending items remain, or `'completed'` if it was the last one). **Per the epics' own deferral note, already correct and unchanged:** this flow does not check an Achievements tab — Story 8.5 is deferred post-MVP.
   5. `backgrounded-recovery.yaml` — independently signs in (same pattern), adds its own pending ladder item via the standalone ladder editor (so it is not dependent on flows 2/3 having left one behind), starts a session through to the active-exposure screen, backgrounds the app, re-foregrounds it, and verifies: the Calm Me FAB (accessibilityLabel `"Calm Me"`) is present and tappable, the session is still on the active-exposure screen (not an error/fallback state), and no error toast is shown. **Correction to epics' "verify... the Calm Me prompt is overlaid":** there is no automatic Calm Me overlay/prompt triggered by backgrounding — the FAB is simply still present and functional, same as on every other screen it's mounted on (`app/_layout.tsx:101`). Assert FAB presence/tappability, not a prompt that does not exist in the implementation.

3. **Given** network state during the smoke suite **When** flows run in CI **Then** all flows run with network connectivity to the local Supabase backend (see AC1); no flow simulates airplane mode or network drops — offline path testing is Story 9.2's integration-test responsibility, not Maestro's.

4. **Given** a flow fails in CI **When** the pipeline result is reviewed **Then** Maestro's own failure artifacts (screenshot + recording at the point of failure — built into `maestro test`, no extra config needed beyond pointing `--output`/the CI step at a directory) are uploaded via `actions/upload-artifact@v4` with `retention-days: 7`; the failed flow name and failing step are visible in the CI job summary (Maestro's CLI output already reports this — surface it via the job's own log, no special parsing required unless the dev agent finds the raw output too noisy, in which case a short `scripts/ci/` post-processing step is acceptable but not required).

### Review Findings

_Adversarial review of this spec document (Blind Hunter + Edge Case Hunter layers; no Acceptance Auditor — there is no separate spec to audit this against, this document is the spec). 14 patch, 2 defer, 6 dismissed as noise._

- [x] [Review][Patch] Inbucket vs. Mailpit API mismatch — `fetchOtp.js` targets the wrong mail service entirely [9-5-e2e-smoke-test-suite-maestro.md:51]
  - Live-verified against this repo's local Supabase stack (CLI v2.107.0): `supabase status -o env` emits a `MAILPIT_URL`, and `curl http://127.0.0.1:54324/api/v1/mailbox/test` returns `"File not found"` — the local mail tool is Mailpit, not Inbucket. Task 4.1's `fetchOtp.js` plan, the Dev Notes § Maestro JS HTTP client (line 110), and References (line 146, 150) are all written against Inbucket's REST shape (`/api/v1/mailbox/<mailbox>`). `onboarding.yaml` — the only flow exercising the real OTP path — will fail to retrieve any code, not just mis-parse one. Rewrite against Mailpit's actual API (`/api/v1/messages`), and source `MAILPIT_URL` from `supabase status -o env` rather than hardcoding port `54324`.

- [x] [Review][Patch] `fear_ladder_items` is PowerSync-synced; PostgREST seeding may never reach the on-device UI [9-5-e2e-smoke-test-suite-maestro.md:46]
  - `apps/mobile/app/ladder.tsx` writes via the PowerSync local-first adapter (`getAdapter().enqueue(...)`), and `packages/sync/src/schema.ts` declares `fear_ladder_items` as a PowerSync table — the UI reads from the on-device SQLite replica, not Postgres directly. No `EXPO_PUBLIC_POWERSYNC_URL` is set in `apps/mobile/.env`/`.env.local`, and no local PowerSync service exists in `supabase/config.toml` or any docker-compose in this repo. ### On-device vs. server-side state — the key constraint Task 3 is built around

Not all "test fixture state" lives in the same place, and conflating them is the single biggest trap in this story:

- **Server-side (Postgres, seedable via Admin/PostgREST API):** the auth user itself (`auth.users`, via `POST /auth/v1/admin/users`), `fear_ladder_items` rows.
- **On-device only (MMKV, scoped by `userId`, NOT seedable via any API):** `isOnboardingComplete` (`markOnboardingComplete()`, `packages/supabase/src/auth/OnboardingProvider.tsx:95-103`), onboarding progress step, crisis-flagged-in-onboarding, first-home-visit-seen, session-in-progress/intention (the MMKV keys behind the recovery modal — see Story 9.4's `KV_KEYS` inventory).

Because onboarding-complete is on-device, the only way to reach it without re-running the full OTP signup is to actually drive the onboarding UI once (via the DEV-bypass, not OTP) and let it persist to MMKV — which then survives for the rest of the CI job as long as the app isn't reinstalled between flow files. `setup/ensureOnboarded.yaml` (Task 3.3) does exactly this, idempotently: a no-op if a prior flow in the same run already did it, a real one-time click-through if not. This is also why `onboarding.yaml` itself must use a **different** account from `test1@test.com` (a disposable email via real OTP) — it exists specifically to exercise the signup/OTP path the DEV bypass skips entirely, and reusing `test1@test.com` there would conflict with that account also being password-based for the other 4 flows.

### Flow independence

Each of the 5 flow files must be independently runnable, in any order, against a `supabase db reset` backend (confirmed Maestro guidance, not an assumption — see citation below). This is why `ladder-build.yaml`/`exposure-loop.yaml`/`debrief.yaml`/`backgrounded-recovery.yaml` each re-establish their own starting state at the top — via `ensureOnboarded.yaml` (on-device) plus backend-seeding `runScript`s where applicable (Postgres-side) — rather than relying on `onboarding.yaml` (or each other) having already run in the same CI invocation. `scripts/ci/run-e2e-smoke.sh` (Task 2.3) happens to invoke them in a fixed, narrative order for readability, but correctness must not depend on that order — each flow's own leading setup steps are what make it work, not execution order. (This order-independence is a correctness guarantee, distinct from the MMKV-sharing no-op optimization in `ensureOnboarded.yaml`, Task 3.3 — that optimization changes wall-clock time only, never correctness, since each flow's setup is independently idempotent.)

### Maestro JS HTTP client (for OTP retrieval and backend seeding)

Maestro ships a built-in JavaScript HTTP client (wrapping OkHttp) usable from `runScript:` steps — `http.get(url)`, `http.post(url, body, headers)`, etc., with a `json()` helper for parsing responses. This is the mechanism for both Task 3 (backend seeding via direct Supabase Admin/PostgREST calls) and Task 4.1 (fetching the OTP code from Mailpit's REST API, `{MAILPIT_URL}/api/v1/messages`, sourced from `supabase status -o env` — see Task 4.1; the local mail tool is Mailpit, not Inbucket, despite `supabase/config.toml`'s `[inbucket]` section name). This is not the standard web `fetch` API — it's Maestro's own client; consult `docs.maestro.dev/maestro-flows/javascript/make-http-requests` for exact method signatures at implementation time, since this story's research did not capture the precise function signatures.

### Shared setup pattern (`runFlow:` subflows)

Maestro supports extracting common step sequences into a separate `.yaml` file and invoking it via `runFlow: relative/path.yaml`, optionally passing `env:` variables consumed inside the subflow via `${VAR_NAME}`. Use this for: `ensureOnboarded.yaml` (Task 3.3 — DEV-bypass sign-in + complete-onboarding-if-needed, reused by Tasks 5/6/7/8), `addLadderItem.yaml` (Task 5's standalone-editor "add item" sequence, reused by Task 8.2), and `reachDebrief.yaml` (Task 6's full sequence, reused verbatim by Task 7.1). Do not copy-paste step sequences across flow files — extract a subflow the first time a sequence is needed by more than one flow.

### Screen/navigation map (verified against current source, file:line citations approximate — re-confirm exact lines at implementation time since files shift)

- **Auth gate**: `app/(onboarding)/_layout.tsx` redirects to `/(auth)/sign-in` if unauthenticated, to `/(app)` if authenticated + onboarding already complete.

- **Crisis keyword interstitial**: any fear-item description field (`FearItemForm.tsx`, both onboarding and standalone ladder editors) runs `detectCrisisKeywords` on every keystroke against `packages/core/src/crisis/keywords.ts`'s `CRISIS_KEYWORDS` list and redirects to `crisis.tsx` if matched — avoid typing any of those strings in test fixture descriptions.
