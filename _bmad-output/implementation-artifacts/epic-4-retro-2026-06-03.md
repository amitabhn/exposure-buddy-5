## Challenges

### 1. Accessibility findings at review — every story

Story 4.2: `SudsCalibrationWidget` tap-targets rendered inside a `radiogroup` but had no `accessibilityRole="radio"` and no `accessibilityState={{ checked }}`. AC2 specified both explicitly. Both were missing at submission.

Story 4.3: `accessibilityRole="link"` used for in-app navigation buttons (two instances); `accessibilityRole="none"` on item rows hiding content from screen readers. Both caught at review.

Pattern: accessibility requirements are understood at spec time and forgotten at implementation time. The same mechanism that eliminated Edge Function security findings (pre-flight checklist → patterns doc) should be applied here.

### 2. `AuthProvider.tsx` boundary exceeded

`AuthProvider.tsx` was modified in every single story of Epic 4. By end of 4.4 it manages:
- Authentication state and session events (core purpose)
- MMKV persistence and startup sequence
- Erasure request lifecycle (Epic 3)
- Onboarding progress step + complete flag
- SUDS calibration write
- Crisis flag in onboarding
- First home visit seen flag + setter

That is 11 distinct state concerns in a single provider. Epic 3 retro flagged it as "having earned an audit." We audited it and then added 6 more things to it.

Epic 5 will add ERP session state: active thread ID, session phase, SUDS log entries. Adding those to `AuthProvider` creates a de-facto global store. Every component calling `useAuth()` will re-render on every ERP session event.

### 3. PowerSync read path is unresolved for Epic 5

`PowerSyncSyncAdapter` is still a true no-op stub. `PowerSyncProvider` is not in the root layout. Epic 4 worked because we only *enqueued* data — never read it. Story 5.1 (Full Courage Ladder Screen) needs to display live `fear_ladder_items` data. The correct approach (PowerSync local SQLite read via `usePowerSyncQuery`) requires `PowerSyncProvider` in the layout — work not yet scoped to any story.

### 4. `Math.random()` UUID in Story 4.3 vs `crypto.randomUUID()` in Story 4.2

Story 4.2 used `crypto.randomUUID()` (with `jest.spyOn` workaround for Jest). Story 4.3 dev notes said "pure-JS `generateUUID()` — same pattern as assessment.tsx" but assessment.tsx's final implementation used `crypto.randomUUID()`. Story 4.3 shipped `Math.random()`. Two UUID generation strategies now coexist in the onboarding flow.

## Key Insights

1. **The pre-condition checklist pattern is the most effective process improvement in the project's history.** Protect it. No story creation until previous epic's action items are verified complete.

2. **A component accessibility pre-flight checklist — modelled on the Edge Function security checklist — would eliminate a whole category of review findings.** The checklist should live in `implementation-patterns-consistency-rules.md` alongside the Edge Function checklist.

3. **`AuthProvider.tsx` is past its natural boundary.** It served as a growth medium during onboarding (reasonable) but entering an ERP session epic with 11 concerns in one file creates performance and maintainability risk.

4. **PowerSync read path must be scoped to Story 5.1.** The architecture was designed for PowerSync-native reads; `usePowerSyncQuery` on the local SQLite database is the correct approach. `PowerSyncProvider` in the root layout is a Story 5.1 prerequisite.

5. **Test count tracking should be maintained in sprint-status.yaml**, not reconstructed from story completion notes. Cumulative count at Epic 4 end: 90 Jest (15 suites) + 17 Vitest (3 suites).
