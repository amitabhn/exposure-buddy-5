# Story 9.4: MMKV Key Hygiene & Storage Audit

Status: in-progress

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer maintaining client-side storage,
I want a lint rule that prevents raw MMKV string literals and a verified audit showing all sensitive fields use Expo SecureStore,
so that key collisions, data corruption, and unencrypted sensitive storage are structurally prevented (ARC-004, NFR-SEC-01).

- `KV_KEYS` (the shared, user-scoped factory object) already exists at `packages/core/src/constants/kvKeys.ts`, exported via `packages/core/src/index.ts`. **14 entries (corrected by code review, not 11)** — 13 user-scoped factory functions plus 1 device-scoped bare-string constant (`PREVIEW_CHALLENGES`, intentionally has no `userId` arg — see the file's own "Device-scoped" comment). Naming is mostly `domain:noun:${userId}` (or two-arg, e.g. `SESSION_LAST_TECHNIQUE`), but not universally — `FIRST_HOME_VISIT_SEEN` has no colon-separated domain prefix (`first_home_visit_seen:${userId}`). This story adds one more entry, `account:pending_deletion:${userId}` — follows the dominant `domain:noun:${userId}` shape; do not invent a parallel naming scheme.
- `packages/supabase/src/auth/session.ts` separately defines its own **`MMKV_KEYS`** (different name, not `KV_KEYS`) for two device-scoped, pre-auth keys (`AUTH_STATE`, `HAS_AUTHED_BEFORE`) — this is intentional and out of scope for migration; the new lint rule only flags *literal* key arguments, and `MMKV_KEYS.AUTH_STATE` is already a non-literal `MemberExpression`, so it already passes the rule structurally.

### The `'pending_deletion_request'` migration is a real bug fix, not just lint cleanup

The flat MMKV key is read unconditionally at app-bootstrap (`AuthProvider.tsx:163-170`), before the signed-in `userId` is resolved (`getAuthState(mmkv)` runs after, at line 172). If a different user signs in on the same device after a prior user's `requestAccountDeletion()` call left a stale entry (the unconditional best-effort delete at line 290 is wrapped in a swallowing `catch`), the second user's `AuthProvider` could surface the first user's deletion-request record. Scoping the key by `userId` (this story's `KV_KEYS.PENDING_DELETION_REQUEST(userId)`) makes this collision structurally impossible — directly serving the story's own stated purpose ("key collisions... are structurally prevented", ARC-004/NFR-SEC-01) rather than relying on best-effort cleanup. [Source: packages/supabase/src/auth/AuthProvider.tsx:140-188, 241-297]
