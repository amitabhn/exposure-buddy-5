## Successes

**Stub-swap architecture held perfectly.** `IConsentRecordService` and `IDpoService` hot-swapped across Stories 3.2–3.4 without touching any screen code. Three epics of architectural planning delivered on its promise in a single epic.

**DPDPA compliance as engineered constraints, not bolt-on.** `consent_records` INSERT blocked at the RLS layer (no INSERT policy by design), immutability trigger on `dpo_audit_log`, `CHECK (false)` on `analytics_events` stub — these are infrastructure-level compliance enforcement, not app-level checks.

**Story 3.1 as environment validation.** The Epic 2 retro recommendation to use the pure-TypeScript story as environment validation worked exactly as intended. Supabase CLI, turbo, and Vitest confirmed clean before Deno was introduced in 3.2.

**`_shared/auth.ts` pattern.** `extractBearerToken` and `verifyOperatorJwt` extracted into shared Deno utilities in Story 3.3. Story 3.4 reused them without modification — prevented auth bugs from reappearing across nine Edge Functions.

**Model B architecture (DPO-mediated erasure).** When adversarial review flagged "DpoService always returns 401," the correct answer was architectural — regular users should never call the erasure endpoint directly. The DPO-mediated flow is valid DPDPA §13 compliance. The reasoning was documented and held.

**Code review process works.** ~45 patches were real issues. Every security finding in this epic was caught before merge. The process is functioning.

## Challenges

### 1. Security vulnerabilities consistently reaching first draft

Every Edge Function story had high-severity security findings at code review that were not caught during implementation:

**Story 3.3:**
- Missing HTTP method guards on all 3 Edge Functions
- Missing self-erasure guard on `dpo-erase-user`
- `SECURITY DEFINER` function missing `SET search_path` pin (SQL injection surface)
- `dpo-export-user` returning 200 for non-existent target users

**Story 3.4:**
- BOLA vulnerability: `dpo-request-deletion` accepted body-supplied `userId`
- `operatorToken` as `window`-accessible global (XSS exposure) instead of closure
- `dpo-login` matched operator by email only, not `id` — ghost audit attribution possible
- `SUPABASE_URL` injected into HTML template without encoding — JS injection via env var
- `seed.sql` with literal UUID placeholder breaking `supabase db reset`

Root cause: no Edge Function security pre-flight checklist existed at implementation time. Each developer re-derived (or missed) security requirements from scratch.

### 2. AuthProvider MMKV state complexity

Story 3.4 produced three separate MMKV-related findings in `AuthProvider.tsx`:
1. Step B wrote `status: 'completed'` even when `requestErasure()` threw
2. `pending_deletion_request` key never cleared on sign-out (ghost state on next user)
3. Redundant `if (mmkvRef.current)` guard creating silent-skip path

`AuthProvider.tsx` has been modified across five stories and manages auth state, MMKV persistence, session events, and erasure request lifecycle simultaneously. Not broken — but accumulating complexity.

### 3. react-test-renderer version mismatch (pre-existing, now critical)

`react-test-renderer@19.1.4` vs expected `19.1.0` has been listed as "pre-existing, unrelated" since Story 3.1. Acceptable for Epic 3 (mostly Deno/Supabase work). **Not acceptable for Epic 4** which is all React Native components requiring component tests.

### 4. Environment runbook never completed (Action Item 3 from Epic 2)

Supabase CLI setup knowledge lives in Story 3.2 dev notes — detailed and accurate — but not a committed, discoverable file. Each story author had to find it. The action item from Epic 2 was marked incomplete at the start of Epic 3 and remained incomplete.

## Key Insights

1. **Code review catches everything, but security issues need pre-implementation checklists.** The pattern from Epic 2 (async useEffect template → patterns doc) should be applied to Edge Function security: a mandatory checklist at implementation time, not discovered at review time.

2. **JWT-derived identity over body-supplied identity is a standing rule.** BOLA prevention via JWT-exclusive user identification should be a first-class architectural principle, documented in `implementation-patterns-consistency-rules.md`, not rediscovered per story.

3. **`AuthProvider.tsx` has earned an audit.** Five stories of accumulated state changes without a holistic review. Before Epic 4 adds onboarding flows on top of it, the state transitions should be read end-to-end.

4. **Story 3.1 as environment validation was the right call.** This pattern — "first story of a new-runtime epic is pure, minimal, no new tech" — is worth repeating for any future epic introducing a new runtime.

5. **The architecture's stub interfaces were its most valuable feature.** The compliance swap was clean specifically because the stubs were designed to be swapped. This validates the architectural bet made in Epic 2.

## Team Agreements

- Every Edge Function implementation must be run through the security checklist (Action Item 2) before submitting for code review
- JWT-derived identity over body-supplied identity is a standing rule for all user-authenticated endpoints
- `window`-accessible storage is never acceptable for privileged credentials — closure or module-scope variable with no global export
- "Pre-existing, unrelated" test failures that accumulate across an epic must be resolved before the next epic starts if the next epic depends on that test infrastructure
