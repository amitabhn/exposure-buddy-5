## Challenges

### 1. `AuthProvider` agreement broken (second consecutive miss)
The Epic 4 team agreement — "AuthProvider receives no new state until the context split is complete" — was not kept. Story 5.3 added six new methods and a new state field. The provider now manages auth lifecycle, onboarding progress, erasure lifecycle, ERP session state, and debrief MMKV helpers across 17+ concerns. Every component calling `useAuth()` will re-render on every ERP session event in Epic 6. This is a real performance risk.

### 2. Dead-end states in the development loop
Two specific spots where the only recovery is a full app reload:
- `isCompletingSession` flag survives Fast Refresh (VER-5-3-1) — "Finish session" button goes grey and ignores taps
- Recovery modal does not dismiss after Resume on Android (fixed in Story 5.2 code review, but pattern indicates fragility in modal + navigation ordering)

### 3. Stub screens lacked back navigation
Forward-only is correct for therapeutic screens (grounding, pause). But stub screens for future features should not inherit that constraint implicitly. A user hitting a stub with no escape must restart the app. This needs a default rule, not a case-by-case decision.

### 4. Story 5.2 was too large
13 ACs, 5 new screens, a state machine, 4 DB migrations, 2 triggers, a recovery modal, and a spec review that surfaced 8 major decisions. Two stories worth of scope in one. This created disproportionate review overhead and a slow feedback loop during implementation.

### 5. PowerSync wiring commitment missed (second consecutive miss)
Epic 4 retro committed: *"PowerSyncProvider wiring and usePowerSyncQuery for fear_ladder_items is in-scope for Story 5.1 — not an Epic 6 item."* This did not land. `useFearLadderItems` still returns `[]`. The ladder screen shows empty state. This is now Epic 6's most critical dependency.

## Key Insights

1. **Pre-implementation spec review is non-negotiable for complex stories.** The three-layer review (Blind Hunter, Edge Case Hunter, Acceptance Auditor) before implementation — not after — is what kept this epic clean. Protect this practice.

2. **`AuthProvider` is a performance timebomb for Epic 6.** ERP session events fire frequently (every SUDS log, every navigation). Every component using `useAuth()` re-renders. The context split must happen before Epic 6 stories start.

3. **Commitments carried twice are structural, not motivational.** A2 and A3 missed two epics in a row because they were "prep work" that got deprioritised. The fix is to make them acceptance criteria in the first story that depends on them — not standalone action items.

4. **Story size above ~8 ACs needs explicit split review.** Story 5.2 at 13 ACs is the reference case. A simple gate during story creation would have surfaced this.

5. **PowerSync wiring is now Story 6.2's AC, not prep work.** The third time this is deferred would be a planning failure, not a delivery failure.
