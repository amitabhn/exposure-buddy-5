## Intent

**Problem:** The app is pinned to Expo SDK 55 (`react-native 0.83.10`). Epic 16 needs it moved to Expo SDK 57 to complete the upgrade. The intermediate SDK 56 stop carries a confirmed Hermes V1 memory regression affecting `react-native-worklets`/`react-native-reanimated` (both used here); the `expo-upgrade` skill's own guidance is to skip it entirely.

**Approach:** Bump `expo` directly to `expo@57.0.9` or a later `57.x` release (never below `.0.9`, never SDK 56) via `npx expo install expo@<version>` + `npx expo install --fix`. Migrate the app's one `@react-navigation/*` direct import to its `expo-router` equivalent (a breaking change introduced at SDK 56 that still applies crossing from 55 to 57), audit non-Expo-managed native dependencies, run `expo-doctor`, update `ADR-RN-VERSION.md`, and pass the full regression suite. This closes out Epic 16 — no further SDK hop follows.

## Boundaries & Constraints

**Always:**
- Use `npx expo install expo@<version>` + `npx expo install --fix` — never hand-pick Expo-managed dependency versions.
- Land on `expo@57.0.9` or later specifically — confirm the resolved version is not below `.0.9` before proceeding (earlier 57.x patches still carry the Hermes V1 regression).
- Run `npx expo-doctor` post-upgrade; fix or explicitly document every flagged issue in Implementation Notes.
- Run `pnpm turbo typecheck lint test` across the whole monorepo as the primary regression gate.

**Never:**
- Do not install or pass through SDK 56 as an intermediate step.
- Do not opt in or out of Hermes V1 — accept SDK 57's default (which resolves the regression at `.0.9`+ regardless).
- Do not adopt React Compiler, migrate to Native Tabs, or touch `expo-av` — none apply to this codebase.
- Do not change the `@powersync/react-native@1.34.0` pin unless required; if it must change, the PowerSync integration test suite must pass end-to-end first (`ADR-RN-VERSION.md` Upgrade Policy).

## Implementation Notes

- **`expo` resolved to `57.0.25`** (`npx expo install expo@latest`, dist-tag `sdk-57`/`latest` at implementation time) — well above the `.0.9` floor, SDK 56 was never installed. `npx expo install --fix` aligned all Expo-managed dependencies in `apps/mobile/package.json` to SDK 57 (react-native `0.86.3`, react `19.2.3`, expo-router `~57.0.23`, expo-font/-constants/-linking/-localization/-notifications/-splash-screen/-status-bar/-application/-dev-client, `@react-native-community/datetimepicker@9.1.0`, `react-native-gesture-handler`, `react-native-safe-area-context`, `react-native-screens`, plus devDependencies `@expo/config-plugins`, `babel-preset-expo`, `jest-expo`, `typescript`).
- **Root cause found (same class of bug as Story 16.1):** `pnpm-workspace.yaml`'s workspace-wide `overrides` block was still hard-pinning `react-native: 0.83.10` / `react: 19.2.0` (the SDK 55 versions), silently reverting `expo install`'s RN/React bump. Updated both to the SDK 57-resolved versions (`react-native: 0.86.3`, `react: 19.2.3`). Also found and fixed the same stale-pin pattern in `packages/supabase/package.json`: `react`/`react-test-renderer` devDependencies pinned at `19.2.0` (bumped to `19.2.3`), and `expo-secure-store` pinned at a years-stale `~14.0.0` (expo-secure-store now follows SDK-aligned versioning; bumped to `~57.0.4` to match the SDK 57 bundle) — the old pin was resolving a peer-linked `expo-secure-store` instance against `expo@55.0.31` even after the app itself moved to `expo@57`. `apps/mobile`'s own `react-test-renderer` devDependency (`19.2.0`) was also bumped to `19.2.3` to match.
- **`react-native-worklets` exclusion removed.** Story 16.1 had pinned `react-native-worklets` at `0.8.3` via `expo.install.exclude` because `react-native-reanimated@4.2.1`'s peer range was `"0.7 - 0.8"`. At SDK 57, `expo install --fix` bumped `react-native-reanimated` to `~4.5.1`, whose peer range is now `"0.10.x"` for `react-native-worklets` — keeping the old exclusion would have pinned an incompatible worklets version and left the Hermes V1 regression's affected packages in a broken peer state. Removed the exclusion; `expo install --fix` then correctly resolved `react-native-worklets` to `0.10.1` (its jest `resolver.js` is still present at this version, so the existing `jest.resolver` config in `package.json` needed no change). This is also the mechanism by which SDK 57.0.9+ actually resolves the Hermes V1 regression — no Hermes opt-in/out was touched, per the spec's constraint.
- **`@react-navigation/native` → `expo-router` migration:** `apps/mobile/app/_layout.tsx`'s `DefaultTheme`/`ThemeProvider` imports were the only direct `@react-navigation/*` import in the app (confirmed via repo-wide grep; the one other hit, in `app/ladder.tsx:17`, is a code comment, not an import). Per the migration guide's own "check for deprecated imports" step: the mapped target `expo-router/react-navigation` re-exports both symbols but marks them `@deprecated` ("Import `DefaultTheme`/`ThemeProvider` from `expo-router` instead"), so both were imported directly from the top-level `expo-router` package instead (confirmed non-deprecated there via `node_modules/expo-router/build/exports.d.ts`). `_layout.test.tsx`'s `jest.mock('@react-navigation/native', ...)` was folded into the existing `jest.mock('expo-router', ...)` mock. The direct `@react-navigation/native` dependency was removed from `apps/mobile/package.json` after confirming it's not a peer dependency of `expo-router@57` (its peerDependencies no longer list any `@react-navigation/*` package) or any other installed package (only a devDependency of `react-native-screens`, for that package's own tests).
- **Non-Expo-managed native dependency audit (four packages, per Code Map):**
  - `@sentry/react-native` (`~7.11.0`) — peer range `react-native: >=0.65.0` admits `0.86.3`; no upstream compatibility issue found; left unbumped (same version Story 16.1 verified against RN 0.83).
  - `@journeyapps/react-native-quick-sqlite` (`^2.5.2`) — peer deps are unconstrained (`react`/`react-native: '*'`); already suppressed in `expo.doctor.reactNativeDirectoryCheck.exclude` from Story 16.1's investigation (untested-on-New-Architecture flag, functionally verified via full sync/PowerSync test suite); unchanged, full test suite (including PowerSync/sync tests) still green.
  - `@rn-primitives/portal` (`1.4.0`, exact pin) — peer deps unconstrained; no compatibility warning from `expo-doctor` or install; left unbumped.
  - `react-native-draggable-flatlist` (`^4.0.3`) — peer ranges (`react-native >=0.64.0`, `react-native-gesture-handler >=2.0.0`, `react-native-reanimated >=2.8.0`) are all satisfied by the post-upgrade versions; already at latest; left unbumped.
- **`npx expo-doctor`: 18/21 checks pass.** Three flagged, all triaged (none fixed by version-pinning workarounds):
  1. *"packages that should not be installed directly" (`@expo/config-plugins`)* — accepted, same reasoning as Story 16.1: the local `plugins/withIosScene27Compat.js` config plugin needs `mergeContents` from `@expo/config-plugins/build/utils/generateCode`, which is not re-exported through `expo/config-plugins`'s public API at SDK 57 either (re-verified: `expo/config-plugins.js` is still `module.exports = require('@expo/config-plugins')`, and `mergeContents` isn't part of that surface). `@expo/config-plugins` remains a legitimate direct devDependency.
  2. *"no duplicate dependencies installed" (`expo`, `expo-asset`)* — all reported "duplicates" resolve to the identical version (`expo@57.0.25`, `expo-asset@57.0.18`) at different pnpm peer-dependency-hash instances; this is pnpm's isolated `node_modules` layout interacting with packages that declare loose (`'*'`) peer deps, not a real version conflict. A full `rm -rf node_modules && rm pnpm-lock.yaml && pnpm install` (needed anyway — see below) plus `pnpm dedupe` reduced this from ~15 flagged packages down to just these 2, both same-version. Accepted as benign, matching Story 16.1's precedent for this exact check.
  3. *"packages match versions required by installed Expo SDK" (patch mismatches: `react-native-reanimated` 4.5.1→4.5.5 found, `react-native-worklets` 0.10.1→0.10.4 found)* — both are patch-level bumps naturally resolved within this project's own `~4.5.1`/`~0.10.1` semver ranges during lockfile resolution, not hand-picked; accepted, matching Story 16.1's precedent for the equivalent reanimated patch-mismatch finding.
- **Full lockfile regeneration required.** Incremental `pnpm add` calls (from repeated `expo install --fix` runs plus the `pnpm-workspace.yaml` override fix) left stale/duplicate resolutions that a plain `pnpm install` didn't reconcile (`expo-doctor`'s "duplicate dependencies" and "overridden dependencies" checks both failed with ~15 stale packages, including genuinely wrong ones like `@expo/dom-webview@55.0.6` where `expo@57.0.25` requires `~57.0.1`). Ran `rm -rf node_modules {apps,packages}/*/node_modules pnpm-lock.yaml && pnpm install`, which resolved the "overridden dependencies" check entirely and reduced "duplicate dependencies" to the 2 benign same-version cases above. Same root cause and same fix Story 16.1 documented.
- **`app.config.ts` plugin registration:** `expo install --fix` reported it couldn't auto-write the `expo-splash-screen` config plugin into the dynamic `app.config.ts` (only static `app.json` can be auto-patched); added `'expo-splash-screen'` to the `plugins` array manually, after `'expo-font'`.
- **TypeScript 5→6 major bump broke ambient Jest types.** `expo install --fix` bumped the `typescript` devDependency from `^5.8.3` to `~6.0.3` (per SDK 57's dependency validation). This caused `tsc --noEmit` to fail across every `*.test.ts(x)` file in `apps/mobile` with `TS2708: Cannot use namespace 'jest' as a value` / `TS2593: Cannot find name 'describe'` — `@types/jest` was no longer being picked up by TypeScript's automatic ambient-`@types`-folder scan (confirmed via `tsc --listFilesOnly`: `@types/jest/index.d.ts` was absent from the compiled file list, while `@types/react`'s ambient `global.d.ts` still appeared, pulled in via a triple-slash reference chain rather than automatic scanning). Root cause not fully isolated to a specific TS 6.0 changelog item in the time available, but the compiler's own suggested fix (an explicit `types` field) is the standard remedy: added `"types": ["jest"]` to `apps/mobile/tsconfig.json`'s `compilerOptions`. This is scoped narrowly to ambient/global type inclusion and does not affect module-resolved imports (`react`, `react-native`, etc.), which were unaffected before and after.
- **Three additional real type errors surfaced after the Jest-types fix restored visibility** (these were latent, pre-existing type-safety gaps exposed by dependency version bumps within already-accepted semver ranges — not new code, and not caused by hand-picked versions):
  1. `app/(auth)/sign-in.test.tsx:107` — `el.type === 'TextInput'` no longer type-checks against the newer `@types/react`/`react-test-renderer` typing of `ReactTestInstance['type']` (`ElementType`, whose string-literal union no longer includes host component names like `'TextInput'`). Fixed with a type-only cast (`(el.type as unknown) === 'TextInput'`); no runtime behavior change — RN's test renderer still exposes the host type as the string `'TextInput'` at runtime.
  2. `app/session/grounding.test.tsx:80` — RN 0.86's `BackHandler.addEventListener('hardwareBackPress', ...)` handler signature gained a required `HardwareBackPressEvent` parameter (previously zero-arg); the test's `handler?.()` call needed an argument. Fixed by passing a minimal satisfying event object; the app code itself (`() => true` in `app/session/grounding.tsx`) needed no change (a zero-arg function is still structurally assignable to a one-arg handler type).
  3. `src/components/auth/SafetyCheckboxes.test.tsx` — `getAllByRole('checkbox')` return-array indexing (`checkboxes[0]`, `checkboxes[1]`) started failing this project's existing `noUncheckedIndexedAccess: true` check, most likely because the `@testing-library/react-native` version resolved within its existing `^13.0.0` range (13.0.x → 13.3.3) tightened its TS return type from a loosely-typed array to a properly-typed one. Fixed using this codebase's existing convention for this exact situation (non-null assertion, e.g. `checkboxes[0]!`, matching the pattern already used in `app/(auth)/sign-in.test.tsx`).
- **Node floor re-verified, no change needed.** `react-native@0.86.3`'s own `engines.node` is `^20.19.4 || ^22.13.0 || ^24.3.0 || >= 25.0.0`. Root `package.json`'s `engines.node: ">=20.19.4"` and all four `apps/mobile/eas.json` build profiles' `node: "22.13.0"` already satisfy this (20.19.4 matches the first branch's floor exactly; 22.13.0 matches the second branch's floor exactly) — no bump required.
- **`pnpm turbo typecheck lint test`: all 19 tasks pass clean** (run with `--force` to bypass any stale cache from the dependency churn above). Mobile: 40/40 test suites, **452/452 tests passing** — matches the Story 16.1 baseline exactly, zero regressions.

- **Manual on-device/EAS-build smoke test: deferred**, as anticipated in Epic 16 context. This environment has no working iOS Simulator GUI (`@expo/cli` hardcodes an old Simulator.app name against the renamed `DeviceHub.app`) and no real interactive terminal for EAS build credential setup (both pre-existing, previously confirmed limitations, unrelated to this upgrade). `npx expo export --platform ios` (above) is the substitute verification, per the spec's own fallback. **Trigger for the full manual smoke test:** before the next `preview`/`development` build produced from this branch is distributed to testers or used for any on-device verification — at that point, sign in, load the home screen, and start one ERP session, confirming no visual/behavioral regression versus the SDK 55 baseline.
